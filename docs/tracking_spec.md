# Спецификация трекинга (Задачи 4–5): идентификаторы, передача, стыковка

## 1. Идентификаторы

| Уровень | Формат | Пример | Кто создаёт |
|---|---|---|---|
| campaign_id | `cmp_<yyyy-mm>_<slug>` | `cmp_2026-09_pro_launch` | маркетолог при планировании |
| placement_id | `p_<channel>_<mmdd>[_<n>]` | `p_ext_ds_memes_0904`, `p_own_1880` | реестр (одна строка = одно размещение) |
| creative_id | `cr_<offer>_<variant>` | `cr_sale_2for14950_v2` | маркетолог; версия текста/оффера |
| promo_code | `<CHANNEL><MMDD>` | `MEMES0904` | генерируется из placement_id, уникален для размещения |
| user_hash | `sha256(telegram_user_id + salt)[:16]` | `4442b0c2696beaf9` | бот; PII не хранится |
| username_hash | `sha256(lower(username) + salt)` | — | бот; мост к `student_id` в слое продаж |

Правило: **payload = placement_id** (≤ 64 символов, `[A-Za-z0-9_-]`) — из него однозначно восстанавливаются канал, кампания
и креатив через реестр. Один креатив в двух каналах = два placement_id.

## 2. Способы передачи источника пользователю → системе

| Механизм | Где применим | Что логируем | Качество связки |
|---|---|---|---|
| Deep-link бота `t.me/<bot>?start=<placement_id>` | внешняя реклама, посты своего канала, YouTube-описание | `bot_start` + user_hash + payload | deterministic |
| Ссылка на чат с pre-filled текстом `t.me/m/<link>?text=#<placement_id>…` (Telegram Business) | посты своего канала, где хотим сразу в диалог | менеджер копирует код одним нажатием кнопки → `manager_chat_open` | deterministic |
| Уникальная инвайт-ссылка в канал на размещение (`t.me/+…`, создаётся в настройках канала) | внешняя реклама с целью «подписка» | `invite_join` (Telegram показывает статистику по ссылке; для user-level нужен бот-админ) | deterministic (join), probabilistic (join→покупка) |
| Промокод креатива | любой пост, видео, сторис | `promo_code_used` при оплате | deterministic |
| Кнопки «Откуда узнали?» у бота / менеджера | когда пользователь пришёл «из ниоткуда» | `source_self_reported` в fact_lead | self_reported |
| Временная близость: join по ссылке размещения → диалог ≤ 48 ч | нет ни одного из ключей выше | placement_id с `match_quality=probabilistic` | probabilistic (вес 0.5 в атрибуции) |

## 3. Ограничения Telegram и как их обходим

* Нет cookies/UTM внутри Telegram-клиента → единственный «параметр» — `start`-payload бота или текст сообщения.
* Пользователь может читать канал днями: касание «прочитал пост» не наблюдаемо на user-level → фиксируем только
  действия (клик по ссылке, /start, сообщение менеджеру). Просмотры поста — агрегат из публичного счётчика (`views_public`).
* Username можно сменить → основной ключ `user_hash` по `user_id`, `username_hash` — вспомогательный.
* Бот не видит, что пользователь написал менеджеру напрямую → кнопка у менеджера «зафиксировать источник»
  (или pre-filled текст). Это операционная дисциплина, а не технология: 1 клик на лид.

## 4. Схема потока (запуск «завтра»)

1. Маркетолог добавляет строку в реестр (`templates/campaign_registry_template.xlsx`): канал, дата/время, cost, креатив, промокод.
2. Скрипт `tracking_bot.py --make-links` печатает deep-link и промокод для строки; они вставляются в креатив.
3. Публикация → бот логирует `bot_start` / лиды; менеджер видит `#placement_id` в первом сообщении.
4. Оплата → в слой продаж пишется `user_hash` (или менеджер вводит `/paid <user_hash> <сумма> <курс>` в группе бота).
5. `attribution.py` + `romi.py` считают ROMI по размещению через 7/14/30 дней; дашборд = `v_romi_by_placement`.

## 5. Что ещё логировать в реестре (иначе ROMI не считается)

`publication_time` (МСК, до минуты), `cost_rub` и `cost_type` (fixed / cpm / barter / opportunity), `views_public`
через 48 ч и 7 дней, `status` (planned / published / deleted — удалённый пост остаётся в реестре!), ссылка на пост,
скриншот креатива (для восстановления истории), `discount_pct`, `deadline` оффера.
