# Продукт и границы MVP

Этот документ описывает целевой продуктовый MVP, а не состояние текущего кода. Фактически реализованные компоненты и ограничения зафиксированы в [архитектуре](ARCHITECTURE.md), разрыв между текущим состоянием и MVP — в [плане](../PLANS.md), принятые решения — в [журнале решений](DECISIONS.md).

## 1. Назначение

Продукт помогает измерять результат собственных рекламных размещений в публичных Telegram-каналах. Он связывает зарегистрированное размещение с переходом в Telegram-бота, лидом и подтверждённой оплатой, после чего показывает результат по кампании и отдельным постам.

MVP предназначен для работы без аналитика и состоит из двух пользовательских контуров:

- локальный веб-интерфейс для маркетолога;
- Telegram-бот для потенциального клиента и менеджера.

## 2. Пользователи

### Маркетолог

- создаёт кампании и размещения;
- задаёт публичный Telegram-канал, дату публикации, стоимость и период анализа;
- получает уникальную deep-link-ссылку для поста;
- запускает сбор постов и пересчёт отчёта кнопкой в локальном интерфейсе;
- смотрит классы и просмотры постов, переходы, лиды, оплаты и атрибутированную выручку.

### Менеджер

- получает в Telegram уведомление о новом лиде с его источником;
- кнопками в уведомлении отмечает лид как оплаченный или потерянный;
- при подтверждении оплаты указывает сумму.

## 3. Сквозной сценарий MVP

1. Маркетолог создаёт кампанию и одно или несколько размещений в локальном веб-интерфейсе.
2. Для размещения он указывает канал, пост или планируемую публикацию, дату, стоимость и границы периода анализа.
3. Система присваивает размещению стабильный `placement_id` и формирует `https://t.me/<bot>?start=<placement_id>`.
4. Ссылка публикуется в рекламном посте. MVP работает с любым публичным Telegram-каналом, но отчёт по продажам строится только для зарегистрированных собственных размещений.
5. Переход пользователя по ссылке создаёт касание. Выбор интересующего продукта создаёт лид и уведомление менеджеру.
6. Менеджер переводит лид из статуса `new` в `paid` или `lost`. Для `paid` он обязательно указывает сумму оплаты.
7. При обновлении система предлагает посту класс `promo`, `content` или `external_ad`. Маркетолог может исправить результат автоматической классификации.
8. Система сохраняет первые доступные снимки публичных просмотров не раньше чем через 48 часов и 7 дней после публикации.
9. Маркетолог получает отчёт по кампании и отдельным размещениям/постам.

Deep-link — основной источник атрибуции. Если источник нельзя определить, событие сохраняется как unknown/organic и не приписывается зарегистрированному размещению. Автоматическая генерация и обработка промокодов в MVP не входят.

## 4. Результат MVP

### Постаналитика

Для каждого зарегистрированного размещения отчёт показывает:

- итоговый класс поста и исходный автоматически предложенный класс;
- публичные просмотры через 48 часов и 7 дней;
- число наблюдаемых переходов в бота;
- число созданных лидов;
- число подтверждённых оплат;
- сумму linear-атрибутированной выручки.

Автоматические классы:

| Класс | Содержание |
|---|---|
| `promo` | Продажа, запуск, лид-магнит или нативное продвижение собственного продукта. |
| `content` | Информационный контент без продающего CTA. |
| `external_ad` | Сторонняя реклама, опубликованная в анализируемом канале. |

Автоматический класс и ручная правка хранятся отдельно. Для группировки отчёта используется ручная правка, если она задана, иначе — автоматический класс. До ручного обновления снимок просмотров может отсутствовать.

### Атрибуция оплаты

MVP использует только linear-модель:

1. Для оплаты отбираются размещения с касаниями внутри заданного для соответствующей кампании окна.
2. Касания до предыдущей оплаты пользователя не переиспользуются.
3. Повторные касания одного размещения учитываются как один источник.
4. Сумма оплаты поровну распределяется между оставшимися размещениями.
5. Если подходящих размещений нет, вся сумма относится к unknown/organic.

Сравнение first, last, time-decay и position не входит в пользовательский сценарий MVP и остаётся методическим экспериментом.

Эти показатели описывают наблюдаемый путь по трекинговой ссылке. Они не доказывают, что продажи не произошли бы без рекламы, и не являются оценкой инкрементального эффекта.

Количественные пороги приёмки для MVP не задаются. Обязательный результат — воспроизводимый пользовательский путь от регистрации размещения до отчёта без ручной работы аналитика.

## 5. Вне MVP

- автоматизированные промокоды и сверка источника по промокоду;
- импорт оплат из платёжной системы;
- полноценная CRM и дополнительные стадии воронки;
- ROMI и сравнительный пилот рекламных каналов;
- причинная оценка incrementality;
- анализ конкурентов и произвольных публичных постов без собственного зарегистрированного размещения;
- исследовательские uplift, forecast, сравнение моделей атрибуции и demo-результаты batch-пайплайна.

Сравнительный пилот нескольких рекламных каналов является следующим этапом и описан в [PLANS.md](../PLANS.md#2-сравнительный-пилот-рекламных-каналов). Статус остальных прототипов — в [каталоге экспериментов](../docs/experiment-catalog.md).

## 6. Словарь

| Термин | Значение |
|---|---|
| Кампания | Набор размещений с общей маркетинговой задачей. |
| Размещение | Один рекламный пост в одном канале в определённое время; основная единица отчёта. |
| Касание | Наблюдаемый переход пользователя по deep-link размещения. |
| Лид | Пользователь, который после перехода выбрал интересующий продукт. |
| Оплата | Лид со статусом `paid` и указанной менеджером суммой. |
| Атрибутированная выручка | Сумма оплат, распределённая между наблюдаемыми маркетинговыми касаниями по заданному правилу. |
| Инкрементальная выручка | Выручка, которая не возникла бы без маркетингового воздействия; для её оценки нужен контрольный дизайн. |
